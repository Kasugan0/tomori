### 1.7 候选处置、人工建单与特殊关闭请求

`POST /api/v1/tickets/{ticket_id}/confirm` 的请求体必须包含最终 `fault_type` 和非空 `candidate_decisions`。每项包含 `evidence_id`、`candidate_id` 和 `decision`（`confirmed`、`modified` 或 `rejected`）。`modified` 必须提供该项 `fault_type`，可提供 `manual_note`；改为 `FLICKERING` 或 `ELECTRIC_HAZARD` 时须提供非空 `manual_note`。其他决定不得携带这两个修改字段。

必须对本工单每个故障候选按证据 ID 和候选 ID 的组合恰好提交一次处置；同工单的参考候选可选处置，重复或未知候选会被拒绝。`confirmed` 的参考候选没有故障类型，仅作留痕；最终 `fault_type` 必须来自至少一个保留候选的原始或修改后有效类型。缺少必填字段的旧客户端请求会校验失败，须升级后再确认。

`POST /api/v1/tickets` 人工建单可选 `evidence_ids`，绑定尚未关联工单的证据；JSON 中每个 ID 必须为严格正整数（不接受布尔、字符串或浮点数）。非管理员只能绑定本人上传的证据，管理员可绑定其他上传者的未关联证据；不存在、已绑定、无权使用或内容重复的证据会被拒绝。可选 `candidate_decisions` 使用上述相同的单项格式，但只允许唯一引用本次绑定证据中的真实 AI 候选，可提交其子集；非空决定没有对应绑定候选时会被拒绝。处置写入审计快照。`multipart/form-data` 中 `evidence_ids` 可重复字段、逗号分隔或 JSON 数组传入，`candidate_decisions` 为 JSON 数组字符串。

`POST /api/v1/tickets/{ticket_id}/review-resolve` 选择 `SPECIAL_CLOSE` 时，`reason` 去空白后至少 10 字符；须提供带时区偏移的 `urged_at`、非空 `urged_unit` 和非空 `urge_evidence_ids`。先通过 `POST /api/v1/tickets/{ticket_id}/evidences` 上传凭证，再提交返回的证据 ID；所有 ID 必须属于该工单。其他裁决不能携带这些督促字段。

## 2. 统一错误契约

- **`HTTP_STATUS_BY_CODE`（权威 `34` 个 `error.code`）**：`400`/`401`/`403`/`404`/`409`/`413`/`415`/`422`/`429`/`500`/`503` 全覆盖；所有错误响应 `{"error": {"code", "message", "details"}}`；
- **`details.fallback`**：`fallback.action ∈ {"MANUAL_REPORT"}`、`resubmit_required: true`、`message_key`（`vision.disabled.manual_fallback`/`vision.timeout.manual_fallback`/`vision.failed.manual_fallback`）、**不含 `evidence_ids`**；
- **`requires_inspector_confirmation=true` / `replaces_electrical_safety_check=false` / `ai_is_baseline_mode` / `vision_ready` / `disclaimer`**：每图 `ai_result_json` 恒注入。
