## 1.2 三段式职责边界（**每一位成员都必须能回答**）

**边界不清是越权、返工与角色失衡的根源。** 任何一个角色定义都必须同时写清三件事：

| 段 | 问题 | 写不清的后果 |
|---|---|---|
| **我负责什么** | 我拥有哪些文件 / 哪些判断 | 交付真空：都以为别人在做 |
| **我不负责什么** | 我**明确**不碰哪些文件与判断 | 越权：做了别人的域，且失去独立复核（自己写自己审 = 没有审） |
| **别人怎么找我** | 什么情况下应该派给我 | 域主人闲置，同时活被塞给「响应最快的人」 |

> **「我不负责什么」比「我负责什么」更重要。** 上表 §1.1 的「明确不负责」列不是修辞——每一条都对应一次实际事故或一次越权纠正。

## 1.3 单应用三角色架构（**不是多入口拆两套 SPA**）

| 项 | 决定 |
|---|---|
| 应用形态 | **单个 Vue 3 应用**，一套构建产物 |
| 角色 | `ADMIN` / `INSPECTOR` / `TECHNICIAN` 三角色**共用同一 SPA** |
| 角色区分方式 | `GET /auth/me` 返回 `role_code` + `scope_authorizations[]` → 前端据此渲染菜单与按钮 |
| 路由守卫 | **全局守卫**按 `to.meta.roles` 判定（**非逐条 `requiresAuth`**） |
| 移动端 | `nav-mobile-*` 响应式，**不是独立应用** |

> **为什么不做两套 SPA**：三角色的页面重叠度高（工单详情三种角色都要看），拆两套会立刻产生重复组件与状态同步问题。**一套应用 + 角色驱动渲染是更少的概念。**

## 2.3 零 git 写纪律

**除 `git-keeper` 外，所有成员零 git 写操作。**

| 允许 | 禁止 |
|---|---|
| `git status` / `git log` / `git diff` / `git show` | `git add` / `git commit` |
| `git config --get <key>` | `git reset` / `git stash` / `git rm` / `git mv` |
| `git ls-files` | `git checkout -- <file>` / `git restore` |
| — | `git worktree` / 设 `GIT_INDEX_FILE` |

**`git-keeper` 的独占范围**：`git add` / `commit -S` / `reset` / `stash` / `rm` / `mv` / `checkout -- <file>` / `restore` / `worktree` / `GIT_INDEX_FILE`；`.git/{config,hooks/,objects/,refs/,packed-refs}`。

> **改名/移动文件用文件系统 `mv`/`rm`，不用 `git mv`/`git rm`。** 阶段二起改名属 `git-keeper` 域。

## 2.4 阶段一冻结纪律

**未获 `Lead` 放行（且须经用户审阅裁决后按批次派单），严禁 `git add` / `git commit`。**

阶段一允许的 git 操作仅：
- 只读检查（`status` / `log` / `diff` / `ls-files`）
- `git-keeper` 维护 `.gitignore` / `.team/notes/git-keeper/` / `.team/commit-gate/`

## 2.5 `write_scopes` 是警告不是锁

**工具会提示重叠，但不会阻止同时写入。** 必须显式协调：

1. **派活前**：检查目标文件的现有 `write_scopes` 声明
2. **发现重叠**：先 `send_message` 协调顺序，**不要「先写后说」**
3. **无法协调**：报 `Lead` 裁决，不要自行决定

> 实测事故形态：同一测试文件被三方同时修改，冲突在提交时才发现，返工两轮。

## 2.6 冲突处理与越权纠正

| 情形 | 处置 |
|---|---|
| 两成员写入域冲突 | 提交 `Lead` 裁决 |
| 发现他人越权 | 记录并报 `Lead`，**不自行回滚他人改动**（回滚也是写操作） |
| 契约冲突 | 以 `docs/` 定稿为准，并报 `Lead` |

**纠正方式：不指责，建立检查。**

- 越权发生后，不是「下次注意」，而是**把检查写进流程**（如 `git checkout -- <file>` 加入 `git-keeper` 独占清单）
- **`Lead` 也会犯同类错**（`LEAD.md` 附录 B 记了 7 次判据错误），**说明纪律是对所有人的**

# 三、协作机制

## 3.1 任务板是唯一协调机制

**为什么必须用任务板**：点对点 `send_message` 会导致三个问题——**状态散落**（没人知道全局在做什么）、**无写入范围**（多人改同一文件）、**无依赖顺序**（派了依赖未完成的任务）。

用户曾直接批评：

> 「你作为 lead 从未编辑过任务板进行共享任务，这是你们团队合作模式的缺陷。」

**三个字段的作用与踩过的坑**：

| 字段 | 作用 | 不用的后果（实测） |
|---|---|---|
| `write_scopes` | 声明写入范围 | 不声明 → 同一测试文件被三方同时碰，冲突后才发现 |
| `blocked_by` | 声明依赖关系 | 不声明 → 派了依赖未完成的任务，执行者做到一半才发现前置缺失 |
| `owner` | 责任人 | `claim` 会记成 `lead` 而非执行者，**Lead 指派必须 `reassign`** |

**正确用法**：

```
team_task_create(subject, description, write_scopes, blocked_by)
team_task_update(action="claim", expected_revision)   # 执行者自己认领
team_task_update(action="reassign", owner=<target>)   # Lead 指派时必须 reassign
team_task_update(action="complete", expected_revision)
```

> **`expected_revision` 不是可选的**——它是 CAS 前置条件，防止并发覆盖。

**补充三条**：
- 口头/消息里说的**不算**派工，必须在任务板上。
- 认领后 `status=in_progress`；完成必须 `action="complete"` + 当前 `expected_revision`。
- **`ready=false` 只是任务板显示态**，不代表不能写（`Lead` 已确认）。

## 3.2 派活模板（7 项）

**每一项缺失都对应一次实际事故**：

| # | 项 | 缺了会怎样 |
|---:|---|---|
| 1 | **用户原话**（引用，不改写） | 转述失真：`Lead` 转述 `auditor` 的符号清单，6 个里 2 个不存在、1 个名字不对 |
| 2 | **判据**（从哪来、哪条） | 执行者不知道「什么算完成」，交付后反复返工 |
| 3 | **已知事实**（带出处） | 执行者重复调研已确认的事，或基于错误前提动手 |
| 4 | **纪律**（工具规范、不许做什么） | 越权：`Lead` 自己写文件、跑 `rg` 查符号 |
| 5 | **产出路径 + 结构** | 产出位置不对、结构不符预期 |
| 6 | **时间盒 + 优先级** | 无限期任务，或低优先级任务挤占关键路径 |
| 7 | **工具通道**（符号级操作用什么） | 不指定 → 执行者自选；**符号级任务漏指会退化成 `rg` 字符串替换**——语义边界丢、间接引用漏、误伤字面量 |

**正例**：本项目 `docs/` 阶段一的多份任务卡都包含全部 7 项——用户原话引用、判据、素材路径、纪律、产出路径、时间盒、**工具通道（Serena 符号级操作）**。

## 3.3 汇报模板（4 项）

| # | 项 | 要求 / 反例 |
|---:|---|---|
| ① | **命令原始输出** | **贴真实输出，不是「已通过」**。反例：报 HEAD 哈希两次，都是「用旧记忆值」——实际已前进两条提交 |
| ② | **数字 + 测量命令** | 「17 张表」必须附上产生这个数字的命令。反例：「覆盖率 91.79%」不带 HEAD → 无法判断是否当前值 |
| ③ | **边界声明** | 明确说清「已证实 / 未证实 / 未运行·未审计范围」。反例：「测试全绿」不说「哪些没跑」→ 假绿 |
| ④ | **P0 核实标注** | 涉及 P0 的必须标 `【需独立核实（由 Lead 复核）】`。反例：自评 P0 未经复核就上报 → `Lead` 基于错误优先级调度 |

**核心纪律**：**「贴命令输出」而不是「总结命令输出」**——总结会引入记忆，贴输出不会。而且读者能自己判断「这是什么时候的状态」。

**正确写法**：

```
$ git log --oneline -1
<原始输出>

$ git status --porcelain
<原始输出>
```

> **为什么必须贴原始输出**：本项目 `docs-writer` 曾报「坐标 `ok=37/bad=0`」，实际脚本只验了第一级，8 处内容全错。**「报告通过」和「真的通过」之间差一个原始输出。**

## 3.4 派工判据：域优先于可用性

**事故形态**：`Lead` 因个别成员反复中途失败，把它们的活派给了响应最快的 `git-keeper`——变异验证、方法论写作、docker 命令全部落到 `git-keeper` 头上。**结果：8 个成员里 2 个全程空闲，另外 3 个在做不属于它们的活。**

**规则**：**派工前先问「这个活属于哪个域」，不是「谁现在有空」。**

| 活 | 域 |
|---|---|
| 变异验证 | `auditor` |
| 测试代码（含源码内联测试模块） | `tester` |
| 生产代码（`backend/`、`vision/` 非测试模块） | `backend-dev` / `vision-dev` |
| `web/` | `frontend-dev` |
| `deploy/`、`compose.yaml`、`RUNBOOK.md`、docker 命令 | `dev-ops` |
| `docs/` 非定稿、设计文档、决策文档、方法论 | `docs-writer` |
| git 写操作、`COMMIT-PROTOCOL.md` | `git-keeper` |

**`team_task_create` 必须填 `write_scopes`，且只能派给 `write_scopes` 匹配的成员。**

**归属判据**：**看「产出物的读者是谁」**——
- 读者是**未来的实现者/运维** → 文档域（`docs-writer`）
- 读者是**编译器/测试运行器** → 代码域（对应实现者）
- 读者是**git 历史/审计者** → `git-keeper`（message、协议）
- 读者是**裁决者** → 谁的域谁写，`Lead` 裁决

**为什么「域对照表」不够**：**表是穷举，会漏；判据是推导，能推。** 上表列的是已知的 7 类活，但新活会不断出现——届时用判据推，不要硬套表。

**为什么「谁有空」是错的判据**：响应快不等于做得好。`git-keeper` 被派去做变异验证时，它的域（提交门禁、边界自证）反而没人守；而真正的域主人（`auditor`）空闲着——**这是「用错人」和「浪费人」同时发生**。

## 3.5 成员失败时：退回原主，不转派

**规则**：**成员失败时，把活退回原主（重新唤醒它继续），不要转派给「响应快」的成员。**

**只有两种情况可以转派**：
1. **原主明确无法继续**（如工具故障、环境阻塞）
2. **转派给同域成员**（如 `backend-dev` → `backend-dev` 的 subagent，**不是** `git-keeper`）

**判据**：**转派前问「接手的人是不是这个域的主人」**——不是 → 不转派，唤醒原主。

**为什么「转派给响应快的」是陷阱**：它把「成员失败」这个**临时故障**变成了「职责错位」这个**结构性错误**。临时故障唤醒原主就能修；结构性错误会持续污染后续所有派工（因为被转派者会以为自己「也负责这个」）。

# 四、质量体系：反假绿（**本项目质量体系的核心**）

## 4.1 现象的唯一定义

**现象只有一个：变异后仍全绿。**

## 4.2 八项形态（A–G + `no-op`）

**A–G 是原因**，可以分类、可以继续增加。

```
假绿（现象：变异后仍全绿）
  ├── A 名字骗人              → 测试名字声称覆盖 X，实际不覆盖
  ├── B 模块盲区              → 目标模块没被编译进测试目标
  ├── C 命名错觉              → （文件级）文件名暗示的覆盖面与内容不符
  ├── D 重合掩盖
  │     ├── v1 同输入          → 两个守卫拦同一输入，变红无法归因
  │     ├── v2 顺序            → 执行顺序掩盖了缺陷
  │     └── v3 守卫密度        → 守卫数量掩盖了单个守卫失效
  ├── E 同义反复              → 断言重述实现，而非验证行为
  ├── F 测试不执行被测代码     → ⚠️ 理论形态，本项目暂无实例
  └── G 断言覆盖不足          → 执行了被测代码，但没断言它的输出

no-op（不是假绿，修法相反）
  └── 改动本身无效果
```

**共 8 项 = A–G 七形态 + `no-op`。**

> 🔴 **纪律：本项目不存在 `F1..F14` 形态编号。**
> 唯一的 `F` 编号是 **`F14` = 「技术断言必须带出处」**（见 §4.3），它是**一条独立纪律**，**不是**形态编号。把 `F14` 当成「第 14 种假绿形态」是错误用法。
> **新发现的形态应先问「它是现象还是原因」**：若是原因，挂到 A–G 下；若是新现象，另立一节。

## 4.3 `F14`：技术断言必须带出处

**技术断言**（「库 X 的行为是 Y」「API 返回 Z」「工具不支持 W」）如果没有**代码坐标 / 官方文档 URL / 可复现命令**，**不得作为决策依据**。

**母本实例**：某成员断言「迁移工具只校验 version 存在、不校验 checksum」**无出处**，`Lead` 据此批准了一段重复实现；实现后反向验证，报的其实是该工具**原生**文案——**报错形态反证了检查没生效**。

**推论**：**「不接受转述」不只意味着「不信别人的结论」，还包括「断言没给出处时，不要基于它行动」。**

> **本项目实例（必须记录）**：`frontend-dev` 素材断言「`el-input` 的 `data-testid` 落到根 `<div>`」，其技术依据 `useAttrs({ excludeKeys: containerAttrs })` **在 Element Plus 2.14.8 源码中不存在**。该无出处断言若被采信，会导致全面误改原生控件——**而 `task-13` 的运行时实测 + 源码复核推翻了它**（实际落到**内层原生 `<input>`**）。**这正是 `F14` 要防的形态。**

## 4.4 假绿 vs `no-op`（**修法相反，误判两个方向都有代价**）

| 类别 | 定义 | 修法 |
|---|---|---|
| **假绿** | 测试存在、能跑，但抓不住 bug | **补测试** |
| **`no-op`** | 没有 bug 可抓（改动本身无效果） | **删改动** |

**判据：变异全绿时，第一假设应该是「改动无效果」，不是「测试缺口」。**

> 把 `no-op` 误判为假绿 → 补一堆测试去覆盖一个不存在的 bug；把假绿误判为 `no-op` → 删掉真正需要的改动。

## 4.5 五层「假象」与判据

| 层 | 假象 | 判据 | 实测案例形态 |
|---:|---|---|---|
| 1 | `0 failed` ≠ 通过 | 判据 0 | 测试没跑也 exit 0 |
| 2 | `passed` ≠ 覆盖（测的不是修复点） | 判据 1 | 8/0 全是 encode 侧，删掉 decode 修复照样全绿 |
| 3 | `passed` ≠ 跑了（没编译） | 判据 9 | 5 条测试没 `mod` 声明 → `0 passed; 115 filtered out` |
| 4 | 断言本身无法失败 | 判据 5 | 断言写成「响应码 ∈ {200, 409}」——两个都接受，永不失败 |
| 5 | 测试绕过被测函数 | 判据 12 | 测了辅助函数，没测实际调用点 |

**判据 17（重合掩盖）**：**「覆盖输入空间」和「覆盖守卫的作用」是两件事**——测「守卫 A 拦某类输入」时，必须用「**只被 A 拦、不被 B 拦**」的输入。

# 五、判据体系

## 5.1 坐标四级判据（**`docs-writer` 的核心工具**）

| 级 | 判据 | 失效形态 |
|---:|---|---|
| 1 | 行号存在（在文件范围内） | 越界 |
| 2 | 行内容命中（非空白） | 空行 |
| 3 | 内容与断言语义一致 | 行号对但指向相邻函数 |
| 4 | **产物身份可追溯** | 结论对但归属错（把链 2 产物说成链 1 机制产出） |

> 🔴 **关键教训：「纯脚本只能验第 1 级」。**
> `RUNBOOK.md` 37 处坐标脚本报 `bad=0`，实际 **8 处 compose 坐标内容全错**——第 2/3 级必须人工或独立方复核。**这是 `docs-writer` 自己犯过的错。**

## 5.2 证据强度排序

```
真实运行日志（running N tests + 测试名 + 真实输出）
   > 变异→红→恢复（sha 逐字节）
   > HTTP 响应码 / DB 行 / 消息（真故障注入）
   > 静态列举（--list / rg / sed）
   > 代码结构推断
   > 他人转述
```

> ⚠️ **「过度自纠也是错」**：不要用弱观测推翻强证据。曾有用 `--list`（陈旧编译产物）否定 `running 1 test` 实跑证据的案例——**那本身制造了一次假绿**。

## 5.3 统计口径必须分层

**统计任何东西前，先定义「分子 / 分母 / 排除项」**，并把排除项列出来。

**反例（本项目方法论母本的实测）**：统计某缩写词得 53 处，分口径后——

| 类别 | 数量 | 是我们的标识符？ |
|---|---:|---|
| 标准库 API（`fetch_optional()` 之类） | 43 | ❌ |
| 注释 | 7 | ❌ |
| 测试函数名 | 3 | ❌ |
| **我们的标识符** | **2** | ✅ |

**「53 处里只有 2 处是我们的」——「所有出现」≠「我们的标识符」。**

**扫描粒度必须递进声明**：子串（字符级，会假阳性）→ 段匹配（snake_case 段，仍含测试/域词）→ 定义点（fn/字段/const，真实信号）→ 调用点（被引用处，风险维度）。**不声明粒度，等于默认用最粗的那种。**

> **本项目实例**：`fault_evidences` 的 CHECK 数**必须写「8」并附「分子=DDL 内显式声明 / 排除项含 `NOT NULL`」**，不能只写数字。`17 张表` 必须附「排除 `alembic_version`」。

## 5.4 零命中必须声明维度覆盖

**「`rg` 零命中」只证明「这个模式在这个范围里没有」，不证明「不存在」。**

**实例形态**：`rg 'use crate::auth'` 零命中 → 推断「环已断，能编译」。实际**环维度和可编译维度正交**——提交后 HEAD 编译不过。

**正确做法**：零命中时必须声明「**我搜了什么模式、在什么范围、排除了什么**」。**排除项就是维度缺口。**

## 5.5 检查脚本必须自证有效

**一个永远返回 `ok` 的脚本比没有脚本更危险。**

**实例**：坐标校验脚本 37 处报 `bad=0`，实际 8 处内容全错——**脚本只验第一级，但报告写成了「坐标全对」**。

**验证脚本有效性的方法**：**故意喂一个已知错误的输入，看它是否报错。** 如果喂错了还报 `ok`，脚本就是假绿。

## 5.6 唯一来源原则（**禁止「写在两处的同一个事实」**）

**数字、行数、条数一律只在它的唯一来源里写，引用处只写「以该文件为准」。**

**为什么**：文件一改，引用处的数字就过期，而**没有任何机制会提醒你改**。这与「计数型标题」是同一个病。

> 例：`COMMIT-PROTOCOL.md` 的硬规则条数从 14 涨到 17，任何写死「14 条」的引用处都已过期。**过时的坐标比没有坐标更糟**——读者按旧行号去翻，会翻到无关内容。
