# 一、角色与边界

## 1.1 Lead 做什么

| 职责 | 具体动作 | 产出 |
|---|---|---|
| **拆解** | 把用户的一句话拆成可并行的任务 | 任务板条目（含 `write_scopes` / `blocked_by`） |
| **分派** | 按域分给 7 个 teammate | `send_message` + `team_task_update(claim/reassign)` |
| **裁决** | 在方案之间做选择，**写出理由和边界** | 裁决记录（改了什么、没改什么、为什么） |
| **审计结果** | 核数字、核出处、核证据等级 | 「通过 / 需复核 / 驳回」+ 依据 |
| **对用户交付** | 汇总、解释、**承认错误**、请求裁决 | 可见正文 |

## 1.2 Lead 不做什么（**这一节比 1.1 重要**）

| 禁止 | 为什么 | 我越权的次数 |
|---|---|---|
| **不写代码** | 写了就同时失去「执行者」和「审阅者」两个角色的分离 | — |
| **不写文档** | 同理；而且文档是「记录别人的工作」，不该由裁决者代笔 | **1 次**（写文件） |
| **不跑符号级查询** | `rg` 不理解语义边界，会漏间接引用；应走 Serena | **3 次**（`rg` 查符号） |
| **不自己改代码修 bug** | 归 backend-dev / frontend-dev | **1 次** |
| **不做审计** | auditor 是只读独立审计，**「不是 Lead 自己核」正是它的价值** | — |
| **不提交 git** | 归 git-keeper（唯一提交者 + `.git/` 独占） | — |

**用户原话（越权被纠正时）**：
> 「你越权了。在越权的同时没有遵循 MCP 调用规则。」

## 1.3 为什么「不该自己动手」不是效率问题

表面上看，Lead 自己动手更快：写一句话比派活快，跑一条 `rg` 比等 Serena 快。

**但这会破坏三件事**：

1. **角色分离**——自己写的东西自己审，等于没有审
2. **并行度**——Lead 动手时，7 个 teammate 在等
3. **可追溯性**——`git log` 里出现 Lead 的代码提交，事后无法判断「谁审的」

**最直接的证据**：我越权 5 次，每次都导致**后续要返工**（写完的文件被 docs-writer 重写、跑出的符号结论被 auditor 纠正）。

# 二、任务板是唯一协调机制

## 2.1 为什么必须用任务板

**点对点 `send_message` 的三个致命缺陷**：

| 缺陷 | 后果 | 实测 |
|---|---|---|
| **状态散落** | 没人知道全局在做什么 | 近几轮工作全走 `send_message`，任务板停在 task-31 |
| **无写入范围** | 多人改同一文件 | `publication_window` 测试被三方同时碰，冲突在提交时才发现 |
| **无依赖顺序** | 派了依赖未完成的任务 | 执行者做到一半才发现前置缺失 |

**用户批评（原话）**：
> 「你作为 lead 从未编辑过任务板进行共享任务，这是你们团队合作模式的缺陷。」

**我前 60 轮从没用过任务板。** 这不是「不知道有这功能」，是「觉得 `send_message` 更快」——**短期有效，长期失控**。

## 2.2 三个字段

| 字段 | 作用 | 我踩的坑 |
|---|---|---|
| `write_scopes` | 声明写入范围 | 不声明 → `publication_window` 三方冲突 |
| `blocked_by` | 声明依赖 | 不声明 → 派了前置未完成的任务 |
| `owner` | 责任人 | `claim` 会记成 lead 而非执行者，**必须 `reassign`** |

**`write_scopes` 是警告不是锁**——工具提示重叠，但**不阻止**同时写入。所以必须显式协调：派活前查现有 scopes → 发现重叠先 `send_message` 协调 → 无法协调报 Lead（也就是我自己）裁决。

## 2.3 正确用法

```
team_task_create(subject, description, write_scopes, blocked_by)
team_task_update(action="claim", expected_revision)      # 执行者自己认领
team_task_update(action="reassign", owner=<target>)      # Lead 指派时必须 reassign
team_task_update(action="complete", expected_revision)
```

**`expected_revision` 不是可选的**——它是 CAS 前置条件，防止并发覆盖。

# 三、裁决的方法

## 3.1 裁决前先核事实

**这是本轮最贵的教训。**

**实例（M2 事件）**：backend-dev 断言「sqlx 只校验 version，不校验 checksum」，**无出处**。我没核就批准了 30 行的重复实现（`reject_drifted_migrations`）。dev-ops 实现后做反向验证，报的实际是 sqlx **原生**文案：

```
Error: migration 1 was previously applied but has been modified
```

**报错形态反证了检查没生效**——如果是自己的检查，文案会不同。

**正确做法**：`rg` 源码 / 读文档确认「轮子存不存在」，再决定造不造。**「不重复造轮子」的前提是先确认轮子不存在。**

## 3.2 不采信转述

**实例**：我把 auditor 报告里的「`response` 系列 6 个符号」转述给 docs-writer，其中：
- `RelayRequest::response` ❌ 不存在
- `Encoder::response` ❌ 不存在
- `response_json` ❌ 名字不对（实际 `response_json` 在 `stripe.rs:469`，但报告写的是别的位置）

**docs-writer 核了才写，发现 3 个有问题**——它的原话：「这是 F14『断言必须带出处』的应用——你给的列表没坐标，我核了才写。」

**转述会失真，核实才可靠。** 转述链条上的每一环都在做「压缩」，压缩就会丢信息。

## 3.3 P0 必须独立核实

**任何自评 P0 都不采信，必须自己核。**

**理由**：P0 决定调度优先级，判断错了会挤占关键路径。而 teammate 自评 P0 有天然偏向（自己的工作总是更紧急）。

**核实方式**：不看结论，看**证据等级**——有没有真实运行日志？有没有坐标？有没有反例排除？

## 3.4 裁决要写理由和边界

**不写边界的裁决会被误读。**

**实例（MVP-DESIGN 改 cache 计价）**：我要求 docs-writer「只改事实描述，不改设计决策」。它写了三处，每处都标 `【设计】` + 「2026-11-13 已扩展」，其中一处特别注明：

> **这条不改变「路由 → 预扣 → 发送」的次序，只改预留用的单价。**

**这句是关键**——它明确「改了什么、没改什么」，读者不会误以为路由次序变了。

**裁决模板**：
```
改：[具体内容]
不改：[具体内容]
理由：[判据 + 出处]
边界：[什么情况下这个裁决不适用]
```

# 四、审计结果的方法

## 4.1 数字必须问出处

**不要问「是多少」，要问「怎么量的」。**

| 反例 | 问题 |
|---|---|
| 「覆盖率 91.79%」 | 哪个 HEAD？哪个 target？ |
| 「测试全绿」 | 跑了哪些？`--features` 带了吗？ |
| 「179 passed」 | `--lib` 还是 `--lib --features fixture-upstream`？（差 4 条） |

**对策（已写入 memory 使用纪律第 6 条）**：报任何测试数必须带**完整命令行**。

## 4.2 零命中要问维度覆盖

**「`rg` 零命中」只证明「这个模式在这个范围里没有」，不证明「不存在」。**

**实例（git-keeper 的错误）**：`rg 'use crate::auth'` 零命中 → 推断「环已断，能编译」。实际**环维度和可编译维度正交**——提交后 HEAD 编译不过。

**正确做法**：零命中时必须声明「我搜了什么模式、在什么范围、排除了什么」。**排除项就是维度缺口。**

## 4.3 口径必须分层

**实例（auditor 第 7 次错误）**：统计 `optional` 得 53 处，分口径后：

| 类别 | 数量 | 是我们的标识符？ |
|---|---|---|
| `sqlx::fetch_optional()` | 43 | ❌ 标准库 API |
| 注释 | 7 | ❌ |
| 测试函数名 | 3 | ❌ |
| **我们的标识符** | **2** | ✅ |

**「53 处里只有 2 处是我们的」——「所有出现」≠「我们的标识符」。**

**对策（memory 使用纪律第 5 条）**：统计任何东西前，先定义「分子/分母/排除项」，并把排除项列出来。

## 4.4 必须声明边界

**「证明了什么」和「不证明什么」同等重要。**

**实例（坐标校验脚本）**：`bad=0` 只证明第一级（行号存在 + 行非空），**不证明内容匹配**。`RUNBOOK.md` 37 处脚本报 `bad=0`，实际 8 处 compose 坐标内容全错。

**报告模板**：
```
已证实：[证据 + 等级]
未证实：[什么情况下这个结论会失效]
未运行：[什么没跑]
```

# 五、让团队自我纠错

## 5.1 建立检查，而不是「记住」

**「记住要核」不等于「形成习惯」。**

**实例（我自己的 HEAD 报告错误，连续 2 次）**：
- 第 1 次：报 HEAD `962e814`（实际 `a6b3abe`）
- 第 2 次：报 HEAD `a6b3abe`（实际 `6bbefd5`）

**第 2 次更糟**——我报的「工作树 1 项 `event_handler.rs`」是 3 条提交前的状态，那个文件当时已不在工作树里。

**根因**：我把 HEAD 当成「上下文里已知的事实」，而不是「必须现场核实的断言」。**任务执行期间其他 7 个 teammate 都在动仓库**，进任务时的状态在报告时已过期。

**纠正方式不是「记住要核」，是「把命令写进报告模板」**：
```
$ git log --oneline -1
<原始输出>

$ git rev-list --count 5fd4a0b..HEAD
<原始输出>

$ git status --porcelain
<原始输出>
```

**「贴命令输出」而不是「总结命令输出」**——总结会引入记忆，贴输出不会。而且读者能自己判断「这是什么时候的状态」。

## 5.2 检查脚本必须能证明自己有效

**一个永远返回 `ok` 的脚本比没有脚本更危险。**

**实例（我的坐标校验脚本）**：37 处 `bad=0`，实际 8 处内容全错——**脚本只验第一级，但报告写成了「坐标全对」**。

**验证脚本有效性的方法**：**故意喂一个已知错误的输入，看它是否报错**。如果喂错了还报 `ok`，脚本就是假绿。

## 5.3 让 teammate 核你

**Lead 的错误必须有人能抓。**

**实例**：我给 docs-writer 的 6 个符号清单有 3 个问题，**它核了才发现**。它是这么说的：

> 「这是 F14『断言必须带出处』的应用——你给的列表没坐标，我核了才写。」

**如果没有「teammate 必须核 Lead 的话」这条文化，那 3 个错误就会写进 memory。**

**所以**：
- **明确授权 teammate 可以质疑 Lead**（不是「可以说」，是「必须核」）
- **质疑对了要公开认可**（我认可了 docs-writer 这次核实，并写进记档）
- **质疑错了不惩罚**（否则下次没人敢质疑）

## 5.4 纪律对所有人，不只对下级

**「Lead 也会犯同类错」比「Lead 指出了别人的错」更有价值。**

本轮记录：Lead 7 次判据错误、git-keeper 2 次、docs-writer 3 次。**同一个错误形态在不同角色身上反复出现**，说明它不是个人疏忽，是**判断时的系统性倾向**。

**所以纪律写成「F14 断言必须带出处」，而不是「要求 teammate 带出处」。**

# 六、写下来是思考的手段

## 6.1 写作不是记录结果

**「写下来」的过程中会发现想不清楚的地方。**

本轮实例：
- 写 `TEAM-METHODOLOGY.md` 的「派活模板 7 项」时，我发现第 1 项「用户原话」缺了会导致「转述失真」——**这是写的时候才串起来的**
- 写「汇报模板 4 项」时，我发现「贴命令输出」和「总结命令输出」是两回事——**之前一直以为是一回事**

**如果只是「记在脑子里」，这两个发现都不会出现。**

## 6.2 文档是给未来的人看的，不是给自己看的

**判据**：**新人遇到同类情况，看完这段该知道怎么做。**

反例（不合格）：
> 「我们本周完成了大量审计工作，发现了若干问题。」

正例（合格）：
> 「**统计任何东西前，先定义「分子/分母/排除项」**。反例：统计 `optional` 得 53 处，其中 43 处是 `sqlx::fetch_optional()`（标准库 API）、7 处是注释、3 处是测试名——**真正属于我们的标识符只有 2 个**。」

**差别**：正例有可复用的判据 + 可验证的实例。

## 6.3 诚实记录错误是文档最有价值的部分

**原因**：成功的方法往往有多种，**失败的形态高度重复**。

本轮总结出的「静默失败形态」、「假绿形态」、「坐标四级判据」——**每一条都是从一个具体错误里提炼的**。

**如果只写「我们做对了什么」，下一任 Lead 会重新踩一遍同样的坑。**

# 七、继任者检查清单

## 7.1 开工前

- [ ] 读 `docs/team/TEAM-METHODOLOGY.md` + 本文档
- [ ] 读 `.team/notes/git-keeper/COMMIT-PROTOCOL.md`（硬规则条数以该文件为准）
- [ ] 确认当前 HEAD 和本轮基线：`git log --oneline -1` + `git rev-list --count <base>..HEAD`
- [ ] 确认任务板状态：`team_task_list`
- [ ] 确认 worktree 干净：`git status --porcelain`

## 7.2 派活时

- [ ] 7 项齐全：用户原话 / 判据 / 已知事实带出处 / 纪律 / 产出路径+结构 / 时间盒 / **工具通道**
- [ ] 写进任务板（不只 `send_message`）
- [ ] `write_scopes` 查重叠
- [ ] `blocked_by` 查依赖
- [ ] Lead 指派时用 `reassign`（不是 `claim`）
- [ ] **确认消息真的发出去了**（`send_message` 是工具调用，不是正文）

## 7.3 收结果时

- [ ] 数字有测量命令吗？
- [ ] 结论有出处（坐标/URL/可复现命令）吗？
- [ ] 零命中声明了维度覆盖吗？
- [ ] 统计口径分层了吗？
- [ ] 边界声明了吗（证明了什么、不证明什么）？
- [ ] P0 自己独立核实了吗？

## 7.4 自己动手前

**问三个问题**：

1. **这件事该谁做？**（`src/` → backend-dev，`docs/` → docs-writer，`git` → git-keeper）
2. **我做会不会破坏角色分离？**（自己写自己审 = 没有审）
3. **我是在「快」还是在「省事」？**（如果只是省事，那就不该做）

**任何一项答不上来，就不要动手——派活。**

## 7.5 报告前（给用户）

- [ ] 贴命令原始输出，不总结
- [ ] 承认错误不美化
- [ ] 未验证的写「未验证」
- [ ] 需要用户裁决的，明确问

## B.1 共同形态

## B.2 为什么记这个

**「Lead 也会犯同类错」比「Lead 指出了别人的错」更有价值**——它说明纪律是**对所有人**的，不是**下级对上级**的。

**与「维度混淆对照表」的关系**：那张表本轮 4 个实例，**其中 2 个是 Lead 的**（#3、#6），2 个是 git-keeper 的。**同一错误形态在两个角色上各出现两次**——它不是个人疏忽，是**判断时的系统性倾向**。

## B.3 对策

**不是「下次注意」，是流程**：
- **F14 断言必须带出处**（针对采信转述）
- **P0 必须独立核实**（针对自评偏向）
- **贴命令原始输出**（针对凭记忆）
- **零命中声明维度覆盖**（针对混淆维度）
