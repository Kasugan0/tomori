## 1. 环境准备

| 项 | 版本/口径 | 备注 |
|---|---|---|
| 宿主机 | Linux x86_64 | 本地/远端均适用 |
| `PostgreSQL` | `17.12`（`D-10`） | `compose.yaml`/`init-dbs.sql` 创建 `tomori_dev`/`tomori_test` |
| `uv` | `0.13.7` 远端 / `0.8.14+` 本地 | `/root/.local/bin/uv` 预装，须绝对路径 |
| `pnpm` | `10.x`（`packageManager` pin） | 前端依赖安装 |
| `Python` | `3.12` | `pyproject.toml` `requires-python` |
| `git` | 签名提交（`G`） | `ssh-add` + `ksshaskpass` |
| 远端 GPU | `RTX 4080 SUPER` `32,760 MiB` | `ssh -p 13142`，`/root/autodl-tmp` |
| 磁盘 | `/root/autodl-tmp` `230G` 可用 | 根分区 `overlay 30G` 仅 `7.8G`，不装包 |

### 2.2 `config/application.example.yml`（`config/` 目录）

`config/application.example.yml` 为 `Settings` 字段的 `__PLACEHOLDER__` 模板（与 `.env` 字段一一映射），供 `settings.py` 字段审计与部署参考。**应用实际只加载 `.env` 与环境变量**（`settings.py:22-26` `env_file=".env"`），不读取 `application.yml`；如需生成 `application.yml` 仅供本地留存，`.env` 与 `application.yml` 均已 gitignored，但严禁把真实值写入 `config/application.example.yml` 模板本身。

## 3. 本地启动（`deploy/stack-guard.sh`）

```bash
# 1) 拉起本地 PG 17（127.0.0.1:25432）并校验
./deploy/stack-guard.sh up
./deploy/stack-guard.sh status

# 2) Python 依赖 + Alembic 迁移（先 cp .env.example .env 并填值）
#    --extra vision 安装视觉依赖组（ultralytics/onnxruntime 等，GB 级）；
#    省略时 YOLO 推理不可用，健康检查报 not ready
uv sync --extra vision
uv run alembic -c alembic.ini upgrade head

# 3) 后端 FastAPI（127.0.0.1:18141）——前台运行，占用当前终端
uv run uvicorn tomori.main:app --host 127.0.0.1 --port 18141

# 4) 前端 SPA（127.0.0.1:15173）——需另开一个终端执行
pnpm --dir src/frontend install   # 首次或依赖变更后执行一次
pnpm --dir src/frontend dev

# 5) 健康检查
curl -s http://127.0.0.1:18141/api/v1/health
```

## 4. 远端训练链（`RTX 4080 SUPER`，`/root/autodl-tmp/tomori/`）

在**本地仓库根目录**执行同步，将 `<remote-host>` 替换为实际主机。`rsync` 不读取 `.gitignore`，以下仅同步训练所需的后端源码和依赖清单，不删除远端旧文件：

```bash
rsync -av --exclude='__pycache__/' -e 'ssh -p 13142' src/backend/ root@<remote-host>:/root/autodl-tmp/tomori/repo/src/backend/
rsync -av -e 'ssh -p 13142' pyproject.toml uv.lock README.md root@<remote-host>:/root/autodl-tmp/tomori/repo/
```

以下命令在**远端**执行；先按远端环境配置 `env.sh`，并同步依赖。`--no-sync` 本身不会更新依赖，若依赖同步失败不得继续训练。

```bash
source /root/autodl-tmp/tomori/env.sh
cd /root/autodl-tmp/tomori/repo
/root/.local/bin/uv sync --locked --extra vision

# merged_v8 生成（nc=3：--drop-occluded + --clean-day-mean-v-max 100
#    + --clean-occluded-model + --clean-damaged-lamp-model）
#    输出：6,945 图 5,513/850/582（8:1:1）；leakage_checks 13 项全 0；
#    damaged_dropped_nonlamp_images=111 / damaged_dropped_nonlamp_boxes=176 /
#    damaged_kept_lamp_overlap=1,247（--clean-damaged-lamp-model 灯头过滤）
/root/.local/bin/uv run --no-sync /root/autodl-tmp/tomori/repo/src/backend/tomori/vision/dataset_prep/manifest_cli.py \
  --source "d1=/root/autodl-tmp/tomori/datasets/d1_lamp_state" \
  --source "d3=/root/autodl-tmp/tomori/datasets/d3_streetlamppole" \
  --source "d4=/root/autodl-tmp/tomori/datasets/d4_damaged_lights|preaug=1,rfmode=phash,map=Not Working:1;Working:0" \
  --source "ext_pwd_s6=/root/autodl-tmp/tomori/datasets/ext_pwd_s6" \
  --source "ext_pwd_s9=/root/autodl-tmp/tomori/datasets/ext_pwd_s9" \
  --source "ext_pwd_s1=/root/autodl-tmp/tomori/datasets/ext_pwd_s1" \
  --source "ext_prj_n_8=/root/autodl-tmp/tomori/datasets/ext_prj_n_8" \
  --source "ext_infras_broken=/root/autodl-tmp/tomori/datasets/ext_infras_broken|splits=valid;test" \
  --output-dir /root/autodl-tmp/tomori/datasets/merged_v8 \
  --train-ratio 0.8 --val-ratio 0.1 --test-ratio 0.1 \
  --phash-threshold 6 --seed 42 \
  --clean-day-mean-v-max 100 \
  --clean-occluded-model /root/autodl-tmp/tomori/runs/streetlight_v1/weights/best.pt \
  --clean-damaged-lamp-model /root/autodl-tmp/tomori/weights/best.pt \
  --drop-occluded

# 4)（可选）无 GPU 干跑校验数据 YAML
/root/.local/bin/uv run --no-sync /root/autodl-tmp/tomori/repo/src/backend/tomori/vision/trainer.py \
  --data /root/autodl-tmp/tomori/datasets/merged_v8/data.yaml \
  --model /root/autodl-tmp/tomori/weights/yolo26s.pt \
  --project /root/autodl-tmp/tomori/runs \
  --dry-run

# 5) RTX 4080 SUPER 正式训练 + 双头离线验证/测试 + best_e2e.onnx 导出 + SHA256SUMS
#    streetlight_v5：merged_v8/nc=3/patience=50/mosaic_polish_epochs=20/batch=24/imgsz=1280
#    历史报告记录 epoch 68 峰值及 epoch 118 早停；精修轮次因原目录缺失无法独立确认
#    --model/--project CLI required=True；--batch 固定整数 >=1（默认 --batch 8）
#    历史报告记录 --batch 24；`mosaic_polish_epochs=20` 为报告中的配置值
/root/.local/bin/uv run --no-sync /root/autodl-tmp/tomori/repo/src/backend/tomori/vision/trainer.py \
  --data /root/autodl-tmp/tomori/datasets/merged_v8/data.yaml \
  --model /root/autodl-tmp/tomori/weights/yolo26s.pt \
  --project /root/autodl-tmp/tomori/runs \
  --name streetlight_v5 \
  --imgsz 1280 --epochs 500 --patience 50 --batch 24 --mosaic-polish-epochs 20

```

训练完成后，在**本地仓库根目录**替换远端主机名并执行回传；核对 `metrics.json` 中的权重哈希与清单一致后再部署：

```bash
rsync -av -e 'ssh -p 13142' root@<remote-host>:/root/autodl-tmp/tomori/runs/streetlight_v5/ ./vision/reports/streetlight_v5/
(cd vision/reports/streetlight_v5 && sha256sum -c SHA256SUMS)
```

历史 `streetlight_v5` 的 `metrics.json` 记录的 `best.pt` 哈希 `a557f4a7…` 与 `SHA256SUMS` 中的 `a067b0b0…` 不一致。原精修目录缺失，权重身份与差异原因不可追溯；需重新训练或重建产物，验证权重、指标和导出模型的对应关系。

## 5. 操作指引

### 5.1 角色操作

| 角色 | 关键操作 |
|---|---|
| `ADMIN` | `/auth/login` → `business-rules` 配置 → `tickets/{id}/dispatch` 派工 → `MANUAL_REVIEW` 决断 → `audit-logs`/`notifications` 监控 |
| `INSPECTOR` | `/auth/login` → `POST /tickets/ai-candidates`（1-10 图）→ 逐条确认 `POST /tickets/{id}/confirm` → `POST /tickets/{id}/acceptance` 验收 |
| `TECHNICIAN` | `/auth/login` → `POST /dispatches/{id}/accept`/`reject`（接单后工单即 `IN_REPAIR`，无独立 start 端点）→ `PATCH /repair-processes/{id}` 更新过程 → `POST /dispatches/{id}/complete` |

### 5.2 业务门禁（必须按序）

- 上传：`1..10` 张/`15 MiB`/`40 MP`/JPEG/PNG/WebP → `415 UNSUPPORTED_IMAGE_FORMAT`（伪装）/`415 MEDIA_VIDEO_STREAM_FORBIDDEN`（视频流）/`422 IMAGE_PIXEL_LIMIT_EXCEEDED`（像素）/`413 IMAGE_SIZE_EXCEEDED`（大小）；
- 建票：`AI_CANDIDATE_PENDING` → `confirmed_by_inspector=true`（`V1` 三层强制）→ `PENDING_DISPATCH` → `DISPATCHED` → `IN_REPAIR` → `PENDING_ACCEPTANCE`（`electrical_safety_checked=true` `V2`）→ `CLOSED` 或 `REWORK_PENDING_DISPATCH`/`MANUAL_REVIEW`；
- `repair_deadline_at` 自 `confirm` 起 `+48h`（`D-11`）；`response_deadline_at` 默认 `NULL`；
- 返修 `round_no <= 2` 新轮，`> 2` `MANUAL_REVIEW`；`MANUAL_REVIEW` `24h` 催办 `3` 次 → `DEAD_LETTER`；
- 幂等：`12` 个写端点 `Idempotency-Key` 必需；`notification_tasks` `DEAD_LETTER` `retry`/`acknowledge`。

### 5.4 备份与恢复

```bash
# 在仓库根目录执行；停掉后端和 worker，避免数据库与上传文件跨时点不一致。
# shell 不会自动读取 .env：下面使用的 TOMORI_PG_USER 和 TOMORI_PG_DB
# 若未在 shell 中设置则取默认值；自定义部署须先在 shell 设置实际库名与用户。
# 示例使用 UPLOAD_DIR=./uploads；自定义时须调整归档和解包路径。
mkdir -p backups
TS="$(date +%Y%m%d-%H%M%S)"

# 1) 数据库：pg_dump（custom 格式；数据库容器保持运行）
docker exec tomori-postgres pg_dump -U "${TOMORI_PG_USER:-tomori}" -Fc \
  -d "${TOMORI_PG_DB:-tomori_dev}" > "backups/tomori_dev-${TS}.dump"

# 2) 上传证据目录：.env 的 UPLOAD_DIR（默认 ./uploads，gitignored 但含全部业务证据）
#    必须随库一起备份——只备份数据库会导致恢复后证据文件缺失
tar -czf "backups/uploads-${TS}.tar.gz" uploads/

# 3) 恢复时指定已有备份的时间戳 TS，切勿使用新生成的时间戳。
#    先停后端（uvicorn/worker）断业务连接，确认目标库并备份当前数据。
#    --clean 只清除备份中包含的对象，目标库其他对象仍可能残留；
#    需完整还原时使用事先确认的空目标库。
docker exec -i tomori-postgres pg_restore -U "${TOMORI_PG_USER:-tomori}" \
  --clean --if-exists -d "${TOMORI_PG_DB:-tomori_dev}" < "backups/tomori_dev-${TS}.dump"

# 4) 恢复默认 uploads/；已有同名文件会被覆盖，归档中不存在的旧文件仍会残留。
#    需完整还原时先核对并备份原目录，选择经确认的空目录；自定义 UPLOAD_DIR 时调整路径。
tar -xzf "backups/uploads-${TS}.tar.gz"
```

> `tomori_pgdata` 卷级物理备份须先 `./deploy/stack-guard.sh stop` 离线进行（`docker run --rm -v tomori_pgdata:/data -v "$PWD:/b" alpine tar -C /data -czf "/b/pgdata-${TS}.tar.gz" .`）；日常备份用上面 `pg_dump` + `tar uploads/` 逻辑备份即可。
