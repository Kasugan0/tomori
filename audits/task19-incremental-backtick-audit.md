## 2. ① 反引号根因：机制对，归因错

### 2.1 `lead` 的描述与实测的差异

`lead` 原话：
> `chk(){ if eval "$2" ...; }`，但断言用双引号传入，**双引号内的反引号会被 bash 先做命令替换**

**实测：这 3 条断言的第二个参数，外层全部是单引号，不是双引号。**

```console
$ python3 扫描全部 37 个 chk 调用，判定第1/第2参数引号类型
chk 调用总数 = 37
含反引号的 chk = 3

L22: 第1参数引号='  第2参数引号='      ← 单引号
L24: 第1参数引号='  第2参数引号='      ← 单引号
L68: 第1参数引号='  第2参数引号='      ← 单引号

第2参数=双引号且含裸反引号（立即丢失）= 0
```

单引号内 bash **不做**命令替换。所以 `lead` 说的"传入时就被吃掉"这一层不成立。

### 2.2 真正的机制：`eval` 的第二轮解析

真正的丢失发生在 **`eval` 内部重新解析命令串**时。决定性区别是**裸反引号 vs 转义反引号**：

| 写法 | `eval` 解析行为 | 最终 grep 模式 | 结果 |
|---|---|---|---|
| **裸** `` ` ``（旧版 L68） | `eval` 内双引号里直接触发**命令替换** | `^\|  数量 \| \*\*34\*\*`（`error.code` 被吃成空） | **恒 FAIL**——文档里永远匹配不上 |
| **转义** `` \` ``（旧版 L22/L24） | `eval` 把 `\`` 还原为**字面反引号** | `` 曾用名**：`docs/API.md` ``（**完整保留**） | **断言完全有效** |

决定性实验（`set -x`，不靠肉眼）：

```console
# 裸反引号：被命令替换吃掉
$ eval 'printf "[%s]\n" "^\| `echo X` 数量"'
[^\| X 数量]                                    ← 换成真实命令就是被吃成空

# 转义反引号：完整保留为字面量
$ eval 'printf "[%s]\n" "曾用名**：\`docs/API.md\`"'
[曾用名**：`docs/API.md`]                        ← 完好无损
```

**`eval` 只做一层解析**：外层单引号保证 `chk` 收到的 `$2` 与源码字符一致（`\`` 仍是两个字符），`eval` 执行这一层时把 `\`` 变成字面 `` ` ``，**仅此而已**，不会再触发一次命令替换。

**我最初把这写成「eval 二次解析把转义反引号也吃掉」，是错的。** 那个错误结论来自我早期 `trace.sh` 里多写一层双引号（`eval "grep -qF \"...\`...\`\""`），人为制造了第二层解析。用 `chk` 的真实调用形式重做后，结论如上表。证据：`logs/backtick/clean-mech.log`、`logs/backtick/verify-mode.log`。

### 2.3 逐条判定

| 断言 | 旧版状态 | 现行版 | 我的判定 |
|---|---|---|---|
| `L68 34 错误码`（裸 `` ` ``） | **恒 FAIL** | 已改外层单引号 + 内层转义 | ✅ **`lead` 正确** |
| `L22 API.md 曾用名≠自身`（`` \` ``） | **有效，非假绿** | 写法未变 | ❌ **`lead` 误判** |
| `L24 SCHEMA.md 曾用名≠自身`（`` \` ``） | **有效，非假绿** | 写法未变 | ❌ **`lead` 误判** |

**`lead` 说「含反引号的断言只有这 3 条」是对的**（我穷举 37 个 chk 验证），**但其中 2 条不是假绿**。

**这个误判有实际代价**：若按「3 条全坏」去修，`docs-writer` 会去改两个本来正常工作、且已被 `MU13`/`MU14` 证明有效的断言。**改动有效断言 = 引入风险而无收益。**

**`L22`/`L24` 真正该修的是行号硬编码**，见 §3.3。

### 2.4 关于 `lead` 的检测正则

`lead` 用的 `rg -c 'chk ".*" +"grep.*`'` **在现行版上零命中**，因为它假设外层是双引号，而实际是单引号。**这个正则本身就是漏检源**——它漏掉了真正出问题的写法。
